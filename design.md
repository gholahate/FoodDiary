# Дневник питания — проектная документация (v1)

Стек: **Kotlin Multiplatform (KMP) + Compose Multiplatform + SQLDelight**
Платформы: Android (первично), iOS (порт из общего кода)

---

## 1. Модель данных

### 1.1 Продукт (`Product`)

Единая сущность и для «сырых» продуктов, и для блюд — разделения на разные таблицы нет, есть флаг способа расчёта.

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT (UUID) | PK |
| `name` | TEXT | Название |
| `calc_mode` | TEXT | `MANUAL` \| `COMPUTED` — как считается КБЖУ на 100г |
| `kcal_per_100` | REAL | КБЖУ на 100г. Для `MANUAL` — вводится пользователем. Для `COMPUTED` — **кэшируется**, пересчитывается при изменении состава |
| `protein_per_100` | REAL | — |
| `fat_per_100` | REAL | — |
| `carb_per_100` | REAL | — |
| `yield_grams` | REAL, nullable | Итоговый выход блюда в граммах (нужен только для `COMPUTED`, чтобы делить сумму КБЖУ ингредиентов на общий вес) |
| `source` | TEXT | `USER` \| `AI` \| `SEED` — кто создал запись (для будущей AI-интеграции и предзаполненной базы) |
| `created_at`, `updated_at` | INTEGER (epoch) | — |

### 1.2 Состав продукта (`ProductComposition`) — рекурсивная связь

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT (UUID) | PK |
| `parent_product_id` | TEXT | FK → Product.id (блюдо) |
| `ingredient_product_id` | TEXT | FK → Product.id (ингредиент, тоже Product — может сам быть составным) |
| `amount_grams` | REAL | Сколько грамм этого ингредиента входит в блюдо |

**Правила:**
- Глубина вложенности не ограничена (блюдо из блюд из блюд).
- **Обязательна проверка на циклы** при добавлении связи (A→B→C→A запрещено) — делается обходом графа перед вставкой строки.
- Расчёт `COMPUTED`-продукта: рекурсивный обход `ProductComposition`, на каждом уровне КБЖУ ингредиента берётся из его `*_per_100 * amount_grams / 100` (либо, если ингредиент сам `COMPUTED`, из его уже посчитанного кэша — пересчёт идёт «снизу вверх», см. §3).
- Один и тот же `Product` может одновременно: входить ингредиентом в N других продуктов, и напрямую добавляться в дневник — это просто использование одной и той же строки в разных местах, конфликта в модели нет.

### 1.3 Единицы измерения (`ProductUnit`)

Бытовые меры пересчитываются в граммы через продукт-специфичные коэффициенты (у «яйца» «1 шт» ≠ «1 шт» у «банана»).

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT | PK |
| `product_id` | TEXT | FK → Product.id |
| `unit_name` | TEXT | «шт», «стакан», «ст. ложка» и т.п. |
| `grams_per_unit` | REAL | Сколько грамм в одной единице |

Продукт всегда имеет неявную единицу «грамм» (коэффициент 1:1), плюс опционально пользовательские единицы из этой таблицы.

### 1.4 Профиль пользователя (`UserProfile`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT | PK (пока один локальный профиль, но UUID — на будущее multi-user/облако) |
| `name` | TEXT | — |
| `target_kcal` | REAL, nullable | Цель по калориям |
| `target_protein` | REAL, nullable | Цель по белкам |
| `target_fat` | REAL, nullable | Цель по жирам |
| `target_carb` | REAL, nullable | Цель по углеводам |

**Правило из ТЗ**: «можно задать только один параметр» — трактую как: пользователь выбирает **какие** параметры отслеживать (любое подмножество из 4), не обязательно один. Поле = NULL означает «не отслеживается» и не участвует ни в прогресс-барах, ни в графиках. *(См. открытый вопрос в §5 — надо подтвердить трактовку.)*

### 1.5 Дневная запись (`DiaryEntry`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT | PK |
| `product_id` | TEXT | FK → Product.id |
| `entry_date` | TEXT (YYYY-MM-DD) | День, к которому относится запись |
| `amount_grams` | REAL | Кол-во в граммах (уже переведённое из бытовой меры, если использовалась) |
| `unit_used_id` | TEXT, nullable | FK → ProductUnit.id — какая единица была выбрана при вводе (для UX: показать «2 шт» вместо «120 г») |
| `kcal`, `protein`, `fat`, `carb` | REAL | **Снапшот** КБЖУ на момент добавления (amount_grams-масштабированный) |
| `created_at` | INTEGER | Время добавления (для сортировки внутри дня) |

**Почему снапшот, а не пересчёт на лету:** если пользователь позже отредактирует продукт «Гречка» в базе, исторические записи в дневнике за прошлые дни не должны задним числом изменить статистику. Снапшот на момент добавления — стандартная практика трекеров питания.

Без категорий приёма пищи (завтрак/обед/ужин) — по вашему ответу, плоский список за день, сортировка по `created_at`.

## 2. Расчёт итогов и графики

### 2.1 Дневной итог
`SUM(kcal), SUM(protein), SUM(fat), SUM(carb)` по `DiaryEntry WHERE entry_date = X` — простая агрегация, снапшоты уже посчитаны, пересчёт дерева состава не нужен.

### 2.2 Недельный график (главный экран)
Группировка `DiaryEntry` по `entry_date` за последние 7 дней, сумма по каждому дню, 4 линии/столбца (или переключение по параметру).

### 2.3 Экран «Графики» (детальный)
Как в ТЗ — по каждому параметру отдельно, с шагом «день» или «неделя»:
- Шаг «день»: точка = сумма за конкретный день, диапазон дат выбирается пользователем.
- Шаг «неделя»: точка = сумма за календарную неделю (или сумма/7 = среднее — уточнить, см. §5).

## 3. Пересчёт составных продуктов (алгоритм)

Когда пользователь редактирует состав или КБЖУ базового ингредиента:

1. Строим граф зависимостей (`ProductComposition`, направление ingredient → parent).
2. Топологическая сортировка от «листьев» (сырых продуктов) к «корням» (сложным блюдам, которые могут входить в ещё более сложные).
3. Пересчитываем `kcal_per_100` и т.д. для каждого `COMPUTED`-продукта снизу вверх, обновляем кэш в таблице `Product`.
4. **Исторические `DiaryEntry` не трогаем** (см. §1.5 — снапшот).

Это фоновая операция (не блокирует UI), выполняется при сохранении изменений продукта.

## 4. Архитектура проекта (KMP)

```
/shared                          — общий Kotlin-модуль (бизнес-логика, БД, use-case)
  /domain                        — модели, интерфейсы (Product, DiaryEntry, ...)
  /data
    /db                          — SQLDelight схема + сгенерированные Queries
    /repository                  — реализации репозиториев поверх SQLDelight
  /usecase                       — AddDiaryEntry, ComputeCompositeProduct, GetWeeklyStats, ...
  /lookup                        — ProductLookupProvider (интерфейс) — см. §6
  /sync                          — заготовка под облако/бэкенд (см. §7)

/androidApp                      — Compose UI, Android-специфика (DI, MainActivity)
  /ui
    /today                       — рабочий стол "текущий день"
    /history                     — календарь + редактирование дня
    /charts                      — графики
    /profile                     — профиль/цели КБЖУ
    /settings                    — настройки
    /search                      — общий компонент поиска (переиспользуется)

/iosApp                          — заготовка под будущий iOS-таргет (Compose Multiplatform UI можно переиспользовать почти полностью)

/backend (позже, вне MVP)        — сервер для Telegram-бота и облачной синхронизации
```

**Ключевой принцип:** весь код, который не касается непосредственно отрисовки экрана (БД, расчёты, use-case, работа с продуктами/дневником) живёт в `/shared` и не знает об Android/Compose. Это то, что делает порт на iOS и написание Telegram-бота (на том же `/shared`, если бэкенд на Kotlin/JVM или через KMP → JVM-таргет) реалистичным без переписывания логики.

## 5. Открытые вопросы (нужно подтвердить перед стартом кодирования)

1. **«Задать только один параметр КБЖУ»** — я трактовал как «пользователь выбирает произвольное подмножество из 4 параметров для отслеживания» (может быть 1, может 2). Если имелось в виду буквально «строго один параметр цели одновременно» — модель профиля надо упростить до `tracked_param` (enum) + `target_value` (одно число). Подтвердите, какая трактовка верна.
2. **Шаг «неделя» на графике** — сумма за неделю или среднее в день за неделю? Для КБЖУ обычно нагляднее «среднее в день», но нужно ваше решение.
3. **Редактирование истории** — при добавлении/удалении продукта в прошлом дне (не сегодня) — нужно ли это как-то помечать/ограничивать, или полностью равноправно с текущим днём?
4. **Единицы измерения** — задаются вручную пользователем при создании продукта (например, «1 яйцо = 55 г»), верно? Или нужен общий встроенный справочник единиц (стакан = 200мл и т.п.) независимо от продукта?

## 6. Заготовка под AI-поиск продуктов

Интерфейс в `/shared/lookup`:

```kotlin
interface ProductLookupProvider {
    suspend fun search(query: String): List<ProductLookupResult>
}

data class ProductLookupResult(
    val name: String,
    val kcalPer100: Double,
    val proteinPer100: Double,
    val fatPer100: Double,
    val carbPer100: Double,
    val confidence: Float? = null   // для AI-источника — уверенность модели
)
```

MVP: `LocalDbLookupProvider` (поиск по локальной базе, `LIKE %query%` или FTS).
Позже: `AiLookupProvider` (вызов LLM/внешнего API) — подключается тем же интерфейсом, UI не меняется. Результат из AI помечается `source = AI` и требует подтверждения пользователем перед сохранением в базу (чтобы не засорять базу неточными данными без контроля).

## 7. Заготовка под Telegram-бота

Бот не встраивается в мобильное приложение — это отдельный клиент к тем же данным. Для этого:
- `/shared` не должен содержать Android-специфичных зависимостей (уже заложено архитектурой).
- Нужен **бэкенд** (вне MVP), который: хранит те же сущности (Product, DiaryEntry, UserProfile) централизованно, отдаёт API. Локальная Android-БД становится кэшем/офлайн-копией, синхронизируется с бэкендом.
- Бот дергает тот же API, что и мобильное приложение (добавить приём пищи текстом/фото → парсинг → DiaryEntry).
- **Вывод:** MVP делаем локальным (как договорились), но с самого начала выносим доступ к данным через слой репозиториев с чёткими интерфейсами (`ProductRepository`, `DiaryRepository` и т.д.), а не прямые SQLDelight-запросы из UI. Тогда позже реализация репозитория меняется с «локальная БД» на «локальная БД + синхронизация с сервером» без переписывания UI и use-case.

## 8. UI-структура экранов (из вашего ТЗ)

**Нижняя навигация (5 вкладок):** Сегодня · История · Графики · Профиль · Настройки

### Экран «Сегодня»
```
[ Поиск (сверху) ]
┌─────────────────┬─────────────────┐
│  Учтено сегодня  │  База продуктов │
│  (DiaryEntry     │  (Product,      │
│   список)        │   тап → добавить│
│                  │   с указанием   │
│                  │   грамм/меры)   │
├─────────────────┴─────────────────┤
│   Итог КБЖУ за день / цель        │
│   (прогресс-бары по отслеживаемым │
│    параметрам)                    │
├────────────────────────────────────┤
│   Мини-график недели               │
└────────────────────────────────────┘
[ Сегодня | История | Графики | Профиль | Настройки ]
```

### Экран «История»
Календарь → выбор дня → тот же вид, что «Сегодня», но за произвольную дату, с полным редактированием (add/remove DiaryEntry).

### Экран «Графики»
Выбор параметра (ккал/Б/Ж/У) + шаг (день/неделя) + диапазон дат → линейный/столбчатый график.

### Экран «Профиль»
Переключатели «отслеживать этот параметр» + поле цели для каждого включённого.

### Экран «Настройки»
MVP: тема, единицы (метрическая система по умолчанию), позже — синхронизация с облаком, интеграция с Telegram, управление AI-поиском.

## 9. План разработки (предложение)

1. **Шаг 1** — SQLDelight-схема (таблицы из §1) + базовые репозитории в `/shared`.
2. **Шаг 2** — use-case: создание продукта (manual/computed), расчёт композиции с защитой от циклов, добавление в дневник.
3. **Шаг 3** — Compose UI: экран «Сегодня» (без графика) на моковых/реальных данных из БД.
4. **Шаг 4** — Поиск продуктов (локальный, `LocalDbLookupProvider`).
5. **Шаг 5** — Экран «Профиль» + прогресс-бары целей.
6. **Шаг 6** — Экран «История» с календарём.
7. **Шаг 7** — Экран «Графики».
8. **Шаг 8** — Настройки + заготовки интерфейсов под AI/Telegram (без реализации).

Каждый шаг — рабочая сборка, которую можно запустить и потыкать на эмуляторе/устройстве.
